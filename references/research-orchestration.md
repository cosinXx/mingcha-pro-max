# 研究编排协议（Orchestration Protocol）

本文档服务 Phase 0–4：主题解构、shard 拆分、报告结构、收口清单。

## 1. 主题解构与问题树（Phase 0）

拿到主题后，在对话上下文里落一张**定锚表**：

| 字段 | 内容 |
|---|---|
| 研究对象 | 一句话说清"研究什么" |
| 用户原话 | 照抄，不曲解 |
| 边界 | 明确"不研究什么"（如只研究中国市场、只看近 5 年） |
| 用户焦点 | 战略 / 投资 / 学习 / 决策 / 写作素材…（决定侧重） |
| 基准年 | 执行当年；预测窗口 = 当年 +3~5 年 |
| 核心命题 | 1 个，可验证可推翻 |
| 子命题 | 3–6 个，各自有检索要点 |

**问题树示例**（主题：AI 编程助手行业）：

```
核心命题：AI 编程助手正从"代码补全工具"升级为"软件开发全流程代理"，价值向工程协作平台迁移。
├─ P1 市场：规模、增速、付费转化、各国渗透率
├─ P2 技术：模型能力边界、上下文工程、Agent 架构、评测基准
├─ P3 竞争：厂商格局、份额、定价、生态位
├─ P4 商业：商业模式、毛利、单位经济、估值逻辑
├─ P5 政策与合规：代码版权、数据训练合规、安全审查
└─ P6 用户：开发者采纳、体验痛点、组织落地障碍
```

## 2. Shard 拆分规则（Phase 2）

- 选中的 4–6 位专家按**主题相关性**归组为 **2–4 个 shard**，每 shard 2–3 位专家。
- 归组原则：检索通道相近、证据域相近的专家同组（如"技术与产品"共享技术信源，"市场与商业"共享财经信源），减少重复检索。
- 每个 shard 一个 Subagent，端到端负责：检索 → 证据台账 → 标准分片。shard 之间无依赖，必须并行。
- 若某 shard 需要另一 shard 的结论（罕见），在编排时把该结论设为**显式输入**提前给定，或明确该 shard 串行排在后面。
- Subagent 的输出必须是**标准分片**，统一 schema：

```markdown
## [专家 ID] [专家名] — [子命题]
### 判断（1–3 条，每条可验证可推翻）
### 证据（每条：事实 + 来源 URL + 可信度级别 一/二/三 + 数据基期）
### 量化（有数字就上数字，标注口径与单位）
### 数据缺口（查不到什么、为什么）
### 对主线的印证或挑战（一句话）
```

## 3. 报告结构大纲（Phase 4）

合并后的完整 Markdown 报告，按此顺序组织（写进 `parts/` 分片）：

| 分片 | 内容 |
|---|---|
| `01-executive-summary.md` | 执行摘要：核心判断、共识 vs 非共识、三情景速览、给决策者的一句话 |
| `02-background-scope.md` | 研究背景、问题定义、边界、方法说明 |
| `03-findings.md` | 核心发现：按子命题组织，每个子命题先亮判断再给证据 |
| `04-dimension-analysis.md` | 维度拆解：各专家视角章节（技术 / 市场 / 商业 / 政策 / 用户…） |
| `05-cross-validation.md` | 交叉验证：多源互证结果、矛盾信息与消解、Red Team 攻击记录 |
| `06-scenarios-and-risks.md` | 三情景（乐观 / 基准 / 悲观）与风险清单、证伪信号 |
| `07-conclusion.md` | 结论与建议（对应用户焦点：战略 / 投资 / 决策…） |
| `08-references.md` | 参考文献：编号与正文勾稽、可点击 URL |

## 4. 收口清单（Phase 4 完成前逐条核对）

- [ ] 核心判断可验证可推翻，且被证据支撑或明确修正过
- [ ] 每个正文数字有句末引用、台账可追溯、基期标注
- [ ] 数据缺口如实列出，无编造
- [ ] Red Team 攻击已写进"争议与不确定性"
- [ ] 引用编号按首次出现顺序递增，文末参考文献勾稽一致
- [ ] 报告无内部工程术语（不出现 shard/lane/专家 ID 等标签）

## 5. 执行者提醒

报告正文不暴露研究机制：不写"本报告由多个 Agent 并行研究"之外的任何工程细节，不出现专家编号、shard、检索轮次等术语；正文读起来像一位研究总编辑完成的成品。
